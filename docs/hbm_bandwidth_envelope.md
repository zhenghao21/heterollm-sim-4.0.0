# HBM 带宽上界与 DQ 守恒验证

验证日期：2026-11-09

结论：HBM 建模在**内部一致性**上通过全部检查——实测服务速率从不超过配置自身声明的接口上限，顺序流随请求增大收敛到该上限，每个传输字节只计一次、占用互不重叠的半双工 lane。这不构成厂商器件标定，也不能替代对真实 HBM 料号的 AC 对照；`vendor_calibrated=false`。

## 为什么不是“验证准确”

公开 JEDEC 文本的 AC 最小表中，tRCD、tRRD、tFAW、tWTR、tWR 等多项原样留空（`docs/hbm_geometry.md` 已渲染核对，不是文本抽取丢失）。因此配置里的 `tRCD=14 ns`、`tWR=15 ns`、`tRTW/tWTR/tRTP` 从生成时就被标为 `assumption`。**没有厂商 AC 表，就不存在“验证时序数值准确”这条路**，任何声称已校准的结论都缺依据。

能验证的是另一组命题：模型是否自洽、是否会重复计费、是否会凭空超出物理带宽。这些用配置自身就能推出上界，不需要外部器件。

## 上界的来源

`effective_lane_bandwidth_gb_s` 决定一个突发在某条 lane 上占用多久，因此：

```
物理接口 = lanes × 每 lane 带宽 = lanes × burst_bytes / burst_occupancy_ns
```

方向 cap 是另外独立限速的突发起始节奏，这正是模型“交织方向可超过单方向 cap、但不超物理接口”的说法。三组配置的推导量：

| 配置 | lanes | burst 占用 | 物理接口 | 声明读/写 cap | 顺序读上界 |
|---|---:|---:|---:|---:|---:|
| HBM3E reference | 256 | 2.048 ns | 4000 GB/s | 1600/1600 | 1600 GB/s |
| HBM4 reference | 512 | 4.096 ns | 4000 GB/s | 1600/1600 | 1600 GB/s |
| HBM3E uncapped | 256 | 2.048 ns | 4000 GB/s | 4000/4000 | 4000 GB/s |

`uncapped` 把方向 cap 抬到物理接口，使阵列而非声明 cap 成为约束——这是检验阵列本身能否喂满接口的对照。

## 顺序流收敛

单条连续读，按突发数递增（`capture_details=False`，走数值内核）：

| 突发数 | HBM3E | HBM4 | HBM3E uncapped |
|---:|---:|---:|---:|
| 32 | 0.95% | 0.64% | 0.40% |
| 256 | 7.58% | 5.10% | 3.17% |
| 2 048 | 46.5% | 33.9% | 23.9% |
| 16 384 | 87.4% | 80.4% | 71.5% |
| 131 072 | 98.2% | 97.0% | 95.3% |
| 1 048 576 | 99.78% | 96.79% | 99.21% |

小点的低值是合法的：首次激活、行未命中、请求尾部无法填满流水。关键在两端——**没有任何点超过 100%**，且大点收敛到 95% 以上。

HBM4 最后一点低于前一点（97.04% → 96.79%），这是唯一一处非单调。定位结果是 REFpb 刷新：刷新命令数随运行时长超线性增长（262 144 突发时 3 584 条，1 048 576 时 134 144 条）。关闭刷新后同尺寸序列严格单调，收敛到 99.62%。**刷新开销是模型应有的物理代价，不是缺陷**，因此判据改成“无刷新流必须严格单调”，并单独量化刷新成本：

| HBM4，1 048 576 突发顺序读 | 耗时 | 相对无刷新 |
|---|---:|---:|
| 开启 REFpb | 21 667.8 ns | +2.93% |
| 关闭刷新 | 21 051.4 ns | — |

## 随机访问与混合方向

| 场景 | HBM3E | HBM4 | HBM3E uncapped |
|---|---:|---:|---:|
| 随机单突发读，峰值占上界 | 33.9% | 47.9% | 13.5% |
| 交织读写（16 384 突发） | 545.8 GB/s | 707.2 GB/s | 535.6 GB/s |

随机访问恒低于顺序流（上表全部成立）。交织读写允许超过单方向 1600 GB/s，但三组都远低于 4000 GB/s 物理接口，与该建模口径一致；`uncapped` 组的实测反而更低，说明瓶颈在阵列的 bank 并行度与换向，不在声明 cap。

## DQ 守恒

这是本次最硬的一条不变量。每个 32 B 突发在某条 lane 上占用 `burst/effective_lane_bandwidth`，lane 日历必须把每条突发串起来。若出现重叠，就意味着一条 lane 同时服务两个突发。

1 024 读 + 1 024 写、随机散布、启用区间明细（`capture_details=True` 强制走参考控制器）：

- 触发 lane 数 = 全部 256 条
- 计费字节 = 传输字节，完全相等
- lane 累计占用 = 传输字节 / 每 lane 带宽，误差 ≤ 1e-6
- **重叠数 0**
- 单 lane 最大利用率 ≤ 100%
- 读写两个方向都出现，确认是混合而非单一方向

## 边界

- 这些上界由配置推出，**不是**厂商器件的可实现带宽。用真实 HBM 料号替换参数后，上界会随之变化，仍然只证明自洽。
- 未实测真实 GPU 或表征数据，系统级偏差（漏算刷新、tRTW 过于保守）不在这项检查的覆盖范围内。
- 地址映射是 `sid_aware` 线性混合基模型，行命中率的绝对数值不代表任何厂商控制器的散列行为。
- 关闭刷新仅用于分离刷新成本，不作为推荐配置。
