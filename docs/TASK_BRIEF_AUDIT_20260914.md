## 1. 目标、范围与优先级

目标是依据模型结构、权重格式、输入形状、硬件、运行时和调度配置，生成可解释的算子图与执行时间预测。

- **一级研究范围：engine 内部执行。** 包括 GPU、HBM/HBF 及其他内存访问、kernel、KV cache、CPU/GPU 协作、同步、采样、host 建图、驱动提交及边界内的调度等待。
- **二级和三级诊断：server 与 client。** 是否属于 engine 以 §4 的真实计时边界判断，不以“发生在 CPU/OS”或模块名称判断。边界外的网络、编码等开销不得并入算子成本。
- **HBF 参数扫描：** 只改变 engine 内受其影响的内存、KV、kernel 和调度成本；服务端/客户端的独立开销保持分离。扫描结果属于敏感性分析，不自动证明新硬件准确性。

优先级固定为：执行语义与计时口径正确 → 未见场景的预测准确性 → 校准成本与模型复杂度。平均误差下降不能抵销数据泄漏、错误语义、必要证据缺失或覆盖率下降；未获接纳的实验仍须留存，不得当作有效基线。

## 2. 允许信息、校准与采集边界

| 情形 | 可用信息与要求 |
|---|---|
| 同硬件/运行时换模型 | 新模型结构、权重格式、静态形状及已冻结的通用成本模型；不能补测模型专属时延后宣称零校准迁移。 |
| 更换硬件或运行时 | 设备规格及预先规定的通用算子、内存、传输和调度微基准；跨版本复用须满足下述兼容性要求。 |
| 只有新硬件规格 | 可作规格驱动预测，但须标记“未验证”，不得与实测标定同等级表述。 |

**禁止答案拟合。** 不得用目标 LLM 的 TTFT、TPOT、E2E 调整硬件参数、时延倍率或场景专属补丁。模型 SHA、prompt fingerprint 只用于溯源，不能成为时延拟合键。

**方法允许不等于本轮授权。** 通用微基准及独立、具有物理解释的残差模型属于可采用的方法；当前自动循环只能使用已有合格证据，不能启动新 native 采集、native 重测或新微基准。缺少采集证据时记录缺口；只有用户另行明确授权后，才能按预登记方案采集。

**区分来源真实性与性能兼容性。** profile 的 provenance 指实际 binary/DLL、硬件、运行时及采集配置；compatibility 指执行路径、构建参数和性能曲面的可迁移范围。EXE/DLL SHA 与依赖集合能约束来源，不能证明性能等价。跨 binary 复用须有源码路径、构建参数和独立通用微基准支持，并明确允许复用的范围。`profile_gate=blocked` 禁止该 profile 用于正式预测，不否定原始 native 数据在其采集环境下的证据状态。

## 3. 建模对象与约束

顶层架构本身是待检验的建模假设，不因已写入设计文档、通过配置校验、已有实现或已冻结基线而被视为正确。分析既要检查模块实现，也要检查组件划分、接口、聚合粒度和因果关系是否足以表达目标系统；必要时允许修正架构表示和接口契约。

顶层同时覆盖以下对象：

- **硬件架构：** 计算设备、内存与存储层级、组件与互连拓扑、可达性、物理及可用容量、共享缓存/带宽/通道/队列/控制器，以及数据访问、搬运和暂存路径。
- **模型与工作负载：** 模型计算结构、权重和状态规模、输入输出要求、请求到达、并发、批次与并行约束，以及由此产生的工作量和容量需求。
- **运行时架构：** 请求、batch、物理 ubatch、执行上下文和提交/完成事件的职责边界，以及控制面、计算图、调度器与状态更新之间的关系。
- **软硬件映射与反馈：** 工作和数据如何放置、驻留和访问；容量、队列、资源竞争及完成事件如何影响放置、组批、调度和后续工作生成。

硬件从顶层进入分析，不仅提供底层算力、带宽和延迟参数；共享关系、访问路径、容量约束和反馈机制的缺口不能仅靠调整这些参数补偿。反馈须有目标运行时机制或明确推导支持，不能凭空引入新的运行策略。下述执行语义、算子成本和系统调度约束共同适用于这些对象，不限定缺口只能发生在哪一层。硬件建模保持符合项目目标的系统级抽象，不因此强制扩展为周期精确、逐指令或逐包仿真。

### 3.1 执行语义

按锁定版本的 llama.cpp/ggml 实现确定算子、shape、dtype、layout、量化路径、输出行选择、KV/state 生命周期、设备放置、依赖和资源归属。不得按模型名称猜测执行路径；`lm-head` 行数由实际请求的 logits 输出行决定，不能一律设为 prompt 长度或一行。

源码推导、条件投影和实测 native dispatch 是不同证据等级。测试必须检查真正进入成本模型的工作负载及在线调度，而不能只检查新增元数据。共享工作、临时状态和持久状态均须明确由哪个任务计费，防止遗漏或重复。

### 3.2 算子成本

成本形式为 `T_op = f(op, shape, dtype, layout, kernel, hardware, runtime)`。每个参数记录来源、单位、有效域和失效条件；可用证据及采集权限遵守 §2。

Roofline 只作基线与约束。GEMM 效率须考虑矩阵尺寸、分块、并行利用率和 kernel 选择，不能只取峰值算力或峰值带宽。逻辑操作量、数据字节数和物理指令/DRAM 事务量不得混称。

### 3.3 系统调度

依据依赖图、资源竞争、请求到达、batch 策略、设备协作与传输重叠生成时间线。连续 batching、并发 prefill、decode 顺序及共享启动边界须有 trace 或明确推导支持。

stage wall、API wall、kernel wall 可能重叠或互相包含，不能简单相加。NVTX CPU range 或 API wall 不等同于 GPU kernel wall；阶段时间与 kernel 时间之差不能机械追加到算子成本，须追踪关键路径及具体资源等待。

## 4. 统一计时契约

### 4.1 一级：engine

每个请求以同一组边界计算指标：

| 符号/指标 | 定义 |
|---|---|
| `t0` | 已完成 server admission、开始 engine 请求处理的边界；不是 HTTP 到达时间。 |
| `t1`、`tn` | engine 完成首个、最后一个真实输出 token 的边界。 |
| `N` | 实际输出 token 数，不是请求的最大长度。 |
| `TTFT_engine` | `t1 - t0` |
| `TPOT_engine` | `(tn - t1) / (N - 1)`，要求 `N > 1`。 |
| `E2E_engine` | `tn - t0` |

若保存 `engine request end`，必须等于 `tn`，不得包含 response queue 或 socket 写入。`prefill_begin/end` 仅描述阶段范围，不能代替首 token 边界。`prompt_eval_ms`、`eval_ms`、`total_ms` 只有在提取器证明其与所需 marker/counter 同边界时才可用于一级指标。

缺少同边界 marker、源码证明的 counter 或逐 token 时间戳时，标记证据不足，不用 client 值或阶段耗时回填。仿真与原生的一级公式共用 `tools/evaluation_contract.py`；单 token 请求的 TPOT 不适用，不通过删格或伪造数值解决。

### 4.2 二级与三级：server / client

server 分解为 frontend、queue、engine、response；client 另含请求及接收传输。只有证据证明各段边界完整、串行且不重叠时，才可将这些时长相加；否则按实际时间线计算。frontend 包括 HTTP/JSON/tokenizer；queue 包括 admission/排队；response 包括采样后编码、SSE/JSON 和发送。

客户端以 POST 发出、收到首个/最后一个真实非空 token 为对应边界，按上表同形公式计算 `TTFT_client`、`TPOT_client`、`E2E_client`。`[DONE]` 等控制消息不计入主要 E2E，尾部另记。获授权采样时同步保存三套口径；现有证据缺失项如实标明，不补造，也不能互相改名、折算或抵销。

**诊断可以在一级未达标时进行**，以排除边界混入或重复计费；但 server/client 性能优化不得代替 engine 优先目标，也不能据此判定一级通过。

### 4.3 输入、重复与观测

输入 token 数由锁定 tokenizer 确认；记录实际输出长度、EOS 策略、warmup、缓存状态、并发、batch/ubatch 和线程数。固定输出（`ignore_eos=true`）与自然 EOS 分开统计，提前结束不得回填 requested length。

并发场景分别保存各请求边界、逐 token 时间戳及延迟，同时保存 batch 起止和 makespan。新增 NVTX/CUPTI/NSYS 等观测须评估开销；profiling 结果不能冒充无扰动真值。

## 5. 数据隔离、冻结与结果复用

### 5.1 数据角色与预测顺序

| 角色 | 用途与限制 |
|---|---|
| 开发集 | 机制诊断及 §2 允许的通用底层参数工作；目标 LLM 答案不作拟合输入。 |
| 候选比较集 | 未参与本轮假设构造的比较组；开发中已查看过的数据不能因此称为独立盲测。 |
| 最终盲测集 | 模型/场景及评分方案预登记，机制冻结后独立评分；揭盲后不再是盲测。 |

先形成并保存预测，再评分读取 native actual。预测器不得读取待预测场景的原生端到端答案。评分发现差异后，只能据可证伪的源码/结构证据提出下一假设，不能反向拼接成本以匹配答案。

### 5.2 一次冻结与默认开发流程

每个实验运行使用唯一 `run_id`，保存清单、源码/profile/运行时身份、计时契约、预测及评分引用；多进程单元记录从属于同一运行。源码、配置或 profile 变化须建立新运行，不覆盖旧 attempt 或拼接不同候选的结果。

准备阶段对本次实际引用的源码、配置、selection、提取器和评分器建立一次身份快照并保存 SHA。默认开发预测/评分复用已验证绑定，保留必要的结构、有效配置、模型一致性、逐格结果与边界检查，不在 worker、收尾和 score 阶段重复全文核验全部模型/运行库或历史凭据。

`--strict-identity` 是现有入口的显式完整复核选项，不是额外必跑阶段。简化重复校验不等于放弃真实性要求：已知身份冲突必须保留，相关数值最多作为带限制的诊断，不得据此宣称验收通过。复核预算见 §8.3。

GGUF 仿真输入使用与源文件相邻的 `*.gguf.metadata.json` sidecar。sidecar 只保存仿真需要的 header、metadata、tensor directory、metadata/tensor-directory digest 及源文件身份；sidecar 命中时，常规 predict、worker 和 score 路径只读取这个小文件，不解码或扫描 GGUF 权重 payload。首次建立 sidecar 或显式 `--strict-identity` 复核可以完整扫描源文件计算 SHA-256。sidecar 必须绑定源 GGUF 的 SHA-256、大小、mtime、file ID、schema、解析器身份和 sidecar 内容 SHA；任一绑定不匹配都必须拒绝，不能静默回退为旧几何。R0 freeze 保存完整 sidecar 绑定；prediction input identity 和 worker execution 通过 freeze/prediction 引用闭包绑定 sidecar path/SHA、源 GGUF SHA 和 metadata/tensor-directory digest。

### 5.3 两种复用条件不能混淆

| 复用对象 | 条件 |
|---|---|
| 固定 native 原始数据/逐 token 时间戳 | 原生 binary、模型、硬件、运行时配置、prompt/output 策略、计时契约及提取语义与本次比较一致。**仿真器机制或成本代码改变不要求重采 native**；应为新候选生成新预测。 |
| 已保存的基线预测与评分 | 基线冻结源码、成本/profile、静态输入、有效绑定及计时契约均与本轮所需基线相同。满足时按原身份引用，不重跑、不改名为本轮新结果。 |

配对试验除预声明的机制改动外，其他条件必须一致。实验父版本不等于已接纳基线；若引用未接纳版本作局部对照，须明示，并另与当前开发基线比较。

本次循环的 native、freeze、预测、评分和失败证据保持不可改写。R0是固定比较起点，冻结源码、配置、预测和评分按各自身份引用；未闭合的运行记录和身份缺口必须如实保留。只维护必要结果及引用，不为同一事实建立平行 control、bundle、receipt、报告或额外验收框架。

## 6. 泛化范围与结论边界

正式报告至少按模型、硬件、迁移类型分组，并分别说明：

- **Shape 泛化：** 未参与开发的 prompt/output/并发/batch 组合，包括边界附近与区间外样本。
- **跨模型：** 完整留出模型，区分规模变化和架构变化。
- **跨硬件：** 在获授权的通用标定完成、硬件模型冻结后验证目标 LLM。
- **组合泛化：** 新模型与新硬件或未见 shape 的组合。

只有相关维度的组合已被联合验证，且 kernel 路径一致，才称插值；各维度分别落在已见区间内并不足够。其他样本标记外推、回退或不支持。随机拆分相关请求不能替代完整模型、设备或实验组留出。

结论只覆盖实际验证的支持域。缺少第二硬件时跨硬件保持“尚未验证”，不把它变成当前单机目标的隐性无限前置条件。

## 7. 验收门槛与统计判定

### 7.1 指标、汇总和失败分类

每项指标先按逐请求边界计算，再按已冻结评分器规定的层级汇总。当前固定集使用仿真场景内请求指标的中位数，与原生各重复批次场景内请求中位数的中位数比较；不得将并发请求或 token 当作独立重复，也不得改为跨批次直接混池取中位数。本说明不新增仿真重复运行要求。误差公式为：

`APE_i = abs(median(T_sim,i) - median(T_native,i)) / median(T_native,i) × 100%`

TTFT、TPOT、E2E 分别判定；使用未舍入数值，**A门和B门统一要求每格三项 APE 均严格 <25%，等于25%不通过**。两门的覆盖与证据要求分别见 §7.2 和 §7.3。分组中位数/P90、最大误差、有符号误差、绝对毫秒误差、重复间波动均须报告，但不能替代逐格判定；场景误差 P90 与请求延迟 P90 分开命名。门槛针对规定的重复汇总，不要求每次瞬时样本都低于门槛。

| 结论 | 使用条件 |
|---|---|
| 通过 | 对应验收门的数值、覆盖和证据要求全部满足。 |
| 精度失败 | 存在有效且同口径的预测/测量比较，但误差未达标。 |
| 证据不足 | 身份/边界/不确定性不合格，或失败、超时、缺失、非有限值使比较无效。另记具体阶段及原因，不冒充纯精度问题。 |
| 尚未验证 | 未开展该支持域或独立验收所需验证。 |

固定范围内的失败、拒收和缺失格保留在分母与覆盖率中；有数值分数不等于该证据有资格验收。正式结论要求相关证据完整率100%。

### 7.2 A门：固定集开发回归

固定范围为 §10 指向的131格；须在**同一冻结候选版本**取得131/131格、393/393项有效结果，全部满足 §7.1 的点估计误差阈值、同口径边界、必要身份和固定覆盖条件。B门另需的独立性及统计不确定性要求不作为A门的新增前置条件；A门自身的身份、边界或覆盖失败仍不得通过。不得因预测困难缩小范围。小规模试跑只用于判断是否值得继续验证，不代表A门通过。

原始162格中的31格稳定性排除保持单独记录；固定开发集的预测覆盖以131格为分母，稳定性筛选后的native覆盖以原始162格为分母（131/162=80.86%），两者分别报告。固定集通过不等于162格全支持，也不等于独立泛化。少量重复中的低波动只描述已观测样本，不自动证明总体测量不确定性已满足正式验收要求；当前重复证据状态见 §10。

### 7.3 B门：冻结后的独立验收

A门通过后冻结机制和输入，停止针对固定答案继续调整，转入预登记的独立场景/完整留出模型验证。B门的模型、硬件、支持域、场景清单及评分/聚合方案须在揭盲前确定。B门沿用 §7.1 的数值阈值、指标、汇总和失败分类，并要求独立实验批次的统计不确定性支持结论；置信范围跨越门槛时为证据不足，不减去噪声、不引入事后容差。

任何获授权的新采样开始前，冻结采样量、独立实验单位、最多加样次数、联合置信水平（默认95%）及多重比较控制方法。独立实验单位遵守 §7.1；单项95%区间不能声称393项同时95%可信；不能反复查看直到过线，也不能用3批次 bootstrap 制造充分证据的假象。

只有A门已通过而B门证据不足时，状态才为“开发回归达标、独立验收未完成”；记录尚需的采集授权/证据，不重拟合A门替代B门。可继续不影响已冻结验收对象的独立工作，不能暗中改变候选后沿用原验收身份。

### 7.4 相关指标不能当作独立证明

对同一多 token 请求，`E2E_engine = TTFT_engine + (N-1) × TPOT_engine`；该恒等式不要求三个跨重复中位数也满足同样等式，三项必须分别汇总。自然 EOS 用实际 `N`，不同输出长度不混算。

一次性启动或边界差异须在未见输出长度上检查首 token、首个及后续 token 间隔和E2E。正式验收至少保留一个未参与机制构造、且在揭盲前锁定的不同输出长度留出场景，并报告逐 token 间隔误差分布；未经源码和独立 trace 证明的触发条件、生命周期及重复次数，只能写成假设。

### 8.1 分工、恢复与候选数量

ChatGPT 负责规划和独立复审；Codex 负责实施、验证、保留失败与更新检查点。本次以R0为比较起点，首次优化候选记为R1；同一次循环内沿用绑定的任务和对话，不通过新建循环或重置计数延长预算。用户插入的审计/方向调整先处理，保存原机制检查点，不把尚未执行的计划记为完成。

各层都可以存在建模缺口，也都可以成为修复起点。分析应检查现有表示能否表达必要行为，不只在既定架构内部寻找参数修正。该顺序是定位方法，不是新增的逐层验收阶段；针对当前问题逐层检查相关假设，复用未变化且仍适用的证据，允许跨层取证，并在下层证据推翻上层假设时回到上层。无需穷举无关机制，也不要求全系统完全闭合后才允许形成有界候选。

分析须区分观察事实、解释假设和未知项，考虑主要竞争解释，说明机制的触发条件、作用范围、预期行为或计时影响及证伪条件。现有仿真关键路径同样是待验证模型的输出；不能仅因某项工作、共享资源或反馈未出现在其中，就认定其不存在或不重要。端到端残差不能用来反推缺失成本，成本证据遵守 §2 和 §3。

保持项由假说决定。修复组批、融合或资源映射等缺口时，派生的 shape、调用次数、放置或服务需求可以改变；这些变化须预声明并解释。固定比较对象、目标工作负载、计时契约及其余配对条件继续按 §4 和 §5 保护，不得借修正表示暗中改变真实设备规格、目标运行时、固定负载或R0冻结证据。

误差热力图的刷新命令为：

```powershell
.venv\Scripts\python.exe tools/plot_baseline_candidate_heatmap.py `
  --baseline-score <baseline-score.json> `
  --candidate-score <candidate-score.json> `
  --out-dir <heatmap-dir>
```

候选尚未存在时省略 `--candidate-score`；生成器会保留 baseline 数值，并把 candidate 与 delta 标为 `NO CANDIDATE`/灰色，不把缺失候选当作零误差。候选 score 的 cell 集合、三项指标和 schema 必须与 baseline 一致，否则生成失败。
