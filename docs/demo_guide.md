# HeteroLLM Simulator：HBM / HBF / 混合 KV Cache 演示指南

> 目标：在固定模型和真实推理负载形状的前提下，只改变 KV Cache 的驻留策略，比较 HBM、HBF 与混合方案对 TTFT、TPOT、E2E、吞吐、KV 流量和迁移的影响。
>
> 本指南按仓库当前前端的真实控件和本地 API 编写。仿真报告会标记为 `ANALYTICAL`（分析仿真）；它可以支持架构假设和相对比较，但不能把 HBF 的公开上限参数当作已完成的芯片实测。

要向老师展示数值边界，可同时打开 [Native / R0 / 当前仿真对比](native_compare_report.md) 和 [HBF 参数重跑结果](hbf_demo_results.md)。前者说明相对 Native 的误差，后者说明本次 488/27.2 GB/s、4/75 μs 参数下 HBM、HBF、混合候选的结果。

## 1. 演示前准备

在离线电脑上解压 `heterollm-simulator-offline.zip` 后，优先双击包根目录的 `Start-Simulator.cmd`；它会使用包内私有 Python 运行时启动服务，不要求演示机安装 Python、Node.js 或联网。启动后访问 `http://127.0.0.1:8765/`，再执行包根目录的 `Check-Offline.ps1` 做健康检查。

如果使用的是开发工程目录而不是离线包，打开 PowerShell，进入工程根目录。推荐先做一次环境检查：

```powershell
.venv\Scripts\python.exe -m heterollm_sim.cli doctor --json
```

如果没有随包提供 `.venv`，用已经准备好的离线 Python 环境安装本地包：

```powershell
py -3.12 -m pip install . --no-index --find-links .\packages
```

如果离线包目录名称不同，把 `--find-links` 改为实际目录；不要在演示机上使用模型目录的在线搜索功能。

启动本地前端（开发工程）：

```powershell
.venv\Scripts\python.exe -m heterollm_sim.cli ui --host 127.0.0.1 --port 8765
```

浏览器打开 `http://127.0.0.1:8765/`。默认端口是 `8765`；如果端口被占用，可以改成 `8766`，然后打开对应地址。服务端窗口要保持运行，关闭窗口会停止前端 API。

打开页面后，先点击顶部的“设置”，确认运行环境状态为可用。页面顶部的“诊断面板”可以显示 API、场景校验和运行错误；演示时建议保持服务端窗口可见，以便老师看到这是本地可复现的分析服务。

## 2. 认识页面的六个视图

左侧步骤条对应六个视图；校验、分层扫描和运行由顶部按钮触发：

1. **架构**：硬件拓扑、组件参数、端口、链路和硬件预设。
2. **模型**：模型语义组件图和模型预设。
3. **映射**：TP/PP/EP、Rank、KV 驻留策略和运行时控制平面约束。
4. **负载**：真实推理负载形状、请求表和连续批处理参数。
5. **回放**：仿真事件时间线、数据流拓扑和事件详情。
6. **结果**：TTFT、TPOT、E2E、吞吐、资源利用率、KV 流量和 KV 迁移。
顶部的“校验”“KV Cache 分层扫描”和“运行仿真”按钮可以在任意视图触发；建议每次修改后先校验再运行。

页面所有下载结果都通过浏览器下载，不会覆盖工程里的旧报告。常用按钮是“导出 JSON”“导入 JSON”“导入硬件参数”“导出硬件参数”和“导出标准 IR”。

## 3. 载入模型和硬件

### 3.1 载入模型

1. 点击左侧“模型”，再点击“模型预设（Model Presets）”。
2. 使用“本地目录（Local Catalog）”筛选模型；离线演示不要点击“在线搜索（Remote Search）”。
3. 选一个与老师讨论一致的模型，例如 `Qwen2.5-7B`、`Qwen3-8B` 或项目已经准备好的模型预设。
4. 点击模型卡片的“应用（Apply）”。模型预设会替换模型图；并行度、KV 策略和负载策略会保留，但模型专属的旧层映射会被清除。
5. 回到“模型”页，检查 attention heads、KV heads、head dimension、层数、模型支持级别和模型图是否符合预期。

模型卡片的支持级别要写进讲解：`exact` 是目录中有完整结构定义；`analytical_approximation` 是分析近似；`out_of_domain` 只能用于查看或结构讨论，不适合拿来做定量甜点结论。

### 3.2 载入硬件拓扑

1. 点击左侧“架构”，再点击“硬件预设库（Hardware Presets）”。
2. 选择“架构预设 · 替换（Architecture Presets）”页签。
3. 当前可直接载入的示例包括：
   - `local-native-rtx5080-9950x3d-gddr7-ddr5`：本机参考拓扑，适合展示真实本机硬件边界；它的显存是 GDDR7，不应称为 HBM 实测。
   - `nvidia-b200-1gpu-2hbf-2hbm`：B200 + 2×HBF + 2×HBM3E 的分析拓扑，适合展示 HBM/HBF 对比；它是 `analytical_approximation`，HBF 参数使用本次登记的分析坐标：读 488 GB/s、写 27.2 GB/s、读延迟 4 μs、写延迟 75 μs。
   - `nvidia-b200-1gpu-3hbf-2hbm`：为 DeepSeek-V3 BF16 权重容量分析增加的 3×HBF 分析坐标；第三个 HBF 不代表量产 B200 封装拓扑。DeepSeek-V3 的 BF16 权重约 1.34 TB，2×HBF 预设无法完整承载，使用 3HBF 才能做本节的端到端 KV 对比。
4. 点击“查看来源、限制与兼容性”，先读限制说明；需要替换时点击“替换当前硬件（Load）”，确认弹窗。
5. 载入架构预设会替换全部组件、端口、链路、分组和布局，但会保留当前模型与负载；旧 Rank 映射和硬件绑定 Profile 会清理或重建，所以载入后要回到“映射”复核。
6. 在拓扑画布中确认 GPU、HBM、HBF、Host Memory 以及它们的链路。点击组件可以在右侧检查器查看容量、读写带宽、延迟、DMA、证据等级和来源。

本机 RTX 5080 + Ryzen 9 9950X3D 的公开硬件快照保存在 `configs/hardware/rtx5080_9950x3d_public.json`，用于复核来源和观测值；运行时以同一数据已固化的 `local-native-rtx5080-9950x3d-gddr7-ddr5` 架构预设为准，不直接读取该 JSON。

B200 预设中的 GPU↔HBF 链路协议字段是 `HBF`；组件和链路 metadata 同时记录 `physical_transport_protocol=UCIe`，用于说明逻辑服务协议与封装物理承载的区别。

“组件预设 · 追加”只向当前拓扑增加组件或组合，不替换当前架构，适合需要自定义对照硬件时使用。新增组件后必须创建并检查它与 GPU 的链路，否则运行时可能无法到达。

### 3.3 DeepSeek-V3 + 端侧个人助手专项流程

要验证 DeepSeek-V3 在 `edge_personal_assistant` 输入下的 HBM/HBF 甜点值，按以下顺序操作：

1. 在模型预设中应用 `deepseek-v3-671b`（DeepSeek-V3-Base，671B/A37B）。它的支持级别是 `analytical_approximation`：当前模型图保留公开层和专家形状，但 MLA 压缩细节、共享专家和 MTP 辅助图没有完全展开；结果用于相对趋势和容量敏感性分析。
2. 在硬件预设中载入 `nvidia-b200-1gpu-3hbf-2hbm`，不要使用 2HBF 预设做完整 BF16 权重运行。3HBF 是容量扩展的分析坐标，三个 HBF 各 512 GB，参数仍是读 488 GB/s、写 27.2 GB/s、读延迟 4 μs、写延迟 75 μs。
3. 在负载预设中选择 `edge_personal_assistant`：Prompt 1,024、Output 512、Batch 1、Prefill chunk 512。
4. 载入模型或 3HBF 架构后，前端会自动把 routed expert 权重按 layer 轮转到 `hbf0`、`hbf1`、`hbf2`；dense、attention、router 和 embedding 权重由控制平面留在 HBM。打开“映射”页的“运行时控制平面约束 → Weight tensor targets”可以复核这些只读前置目标，不需要现场手工添加几十个 layer 条目。
5. 分别运行 HBM-only、HBF-only 和 HBM 主缓存 + HBF 卸载三种候选。每个候选都必须重新校验并运行，记录 TTFT p50、TPOT p50、E2E p50、KV 峰值、KV 读写流量、Migration、Offload 和 Swap Transfer。

如果误载入 2HBF 预设，容量校验失败是预期边界，不是前端故障：DeepSeek-V3 BF16 权重超过两颗 HBF 与 HBM 的可用总容量。不要通过把容量字段改大来掩盖这个结果；切换到 3HBF 分析坐标，或明确改用另一个已声明精度的量化模型预设。

## 4. 设置真实 AI 负载

点击左侧“负载”。负载预设来自 llama.cpp 对齐基线和项目 35 的典型应用形状，当前本地目录包含：

| 预设 | 输入 Token | 输出 Token | Batch | 适合讲解 |
|---|---:|---:|---:|---|
| `llama_cpp_default` | 512 | 128 | 1 | 轻量单请求基线 |
| `personal_assistant` | 4096 | 1024 | 12 | 长对话、检索和工具调用 |
| `customer_service` | 2048 | 256 | 16 | 短输出高并发 |
| `enterprise_office` | 16384 | 2048 | 8 | 长文档、多租户 |
| `content_creation` | 3072 | 8192 | 16 | 长输出，持续 Decode |
| `software_development` | 24576 | 4096 | 16 | 长上下文代码理解 |
| `search_platform` | 12288 | 768 | 12 | 检索增强、较长上下文 |
| `edge_personal_assistant` | 1024 | 512 | 1 | 低并发短上下文 |

选择预设会重建显式请求表。为了做公平对比，三种 KV 方案必须使用同一个预设、同一个随机种子和同一套调度参数。

在“连续批处理与调度”区域检查：

- **模式**：`持续（Continuous）` 用于模拟连续批处理；只有需要静态批次对照时才选 `静态（Static）`。
- **最大序列数**：对应调度器允许同时服务的请求数。
- **最大批处理 Token 数**：决定批次的 Token 上限；长上下文场景不能只修改最大序列数而忽略它。
- **预填充分块 Token 数**：控制 Prefill 分块，建议先保持预设值。
- **允许抢占**：需要研究高并发内存压力时打开；只比较 KV 介质时先关闭，避免把抢占变化误认为介质收益。

“显式请求”表还可逐请求编辑：请求 ID、到达时间（ns）、Prompt Token、Output Token、优先级和截止时间。用它可以构造不同到达间隔的真实负载。修改显式请求后，合成负载默认值不会覆盖这些请求。

推荐现场先演示三组固定负载：

- `llama_cpp_default`：快速验证流程和 HBM-only 基线。
- `personal_assistant`：放大 KV 容量和迁移差异。
- `content_creation`：放大持续 Decode 的 KV 读取和追加写入。

## 5. 设置三种 KV Cache 方案

点击左侧“映射”，在“并行与 KV 策略输入”中操作。每改一次 KV 策略，界面会标记映射过期；下一次运行时由后端控制平面重新物化实际放置。

### 5.1 HBM-only

这是最稳妥的基线：

1. “KV 驻留模式”选择 **固定单组件（Fixed single component）**。
2. “缓存组件”选择 `hbm0`（若拓扑中有多个 HBM，选择当前 Rank 可达的目标）。
3. “卸载组件”选择 **不卸载（No Offload）**。
4. “每页 Token 数”保持 16 或记录一个固定值；三种方案必须一致。
5. 在右侧控制平面约束中不要填写 `KV Cache target`，让后端按当前固定策略物化；若老师要展示显式控制，可把它也设为 `hbm0`。

运行后，结果页的“KV 容量与放置分析”应显示 `hbm0` 的容量、峰值和层归属，KV 迁移通常为 0。

### 5.2 HBM 主缓存 + HBF 卸载（推荐的默认 HBF 演示）

当前 B200 演示预设已经把 HBF 登记为 **active-memory 分析坐标**，可直接用于 KV-only 和 HBM→HBF 候选扫描。参数是用户指定的可替换分析假设，不是量产 HBF 的持续实测：读 488 GB/s、写 27.2 GB/s、读延迟 4 μs、写延迟 75 μs。

选择“固定单组件”并把“缓存组件”改为 `hbf0`，可以观察 HBF-only；选择缓存 `hbm0`、卸载 `hbf0`，可以观察混合策略。长上下文或高并发下重点看 Offload、Prefetch、Migration 和 Swap Transfer。

active-memory HBF 的运行约束仍然会被校验：`metadata.access_mode = "memory"`、可写标记、正的读写带宽、读写延迟、传输粒度、最大并发请求、显式 Host Memory Profile 以及与 Profile 一致的 `memory_service_owner`。自定义 HBF 如果缺少这些字段，前端会显示不可行，不会静默放宽约束。

### 5.3 混合 KV

混合策略要先确定“混合”的含义：

- **主缓存 + 卸载**：HBM 保存活动页，HBF 在容量压力时接收页。设置为 `固定单组件`、缓存 `hbm0`、卸载 `hbf0`，并保持统一的页大小和调度参数。
- **按层分配**：选择 **手动按 layer 指定（Manual per-layer mapping）**；随后展开“运行时控制平面约束 → 目标约束 → KV layer targets”，按 layer 将目标组件分到 HBM 或 active-memory HBF。该模式不会把两个组件偷偷合并成一个容量池，结果页会按组件显示容量、使用量和层归属。
- **动态 KV Pool**：选择 **动态 KV Pool（实验性）** 只能用于后端明确支持的场景。演示时应把“实验性”写在标题中，不能把它当作已验证的 page-level 自动冷热分层。

混合场景要截图保存“KV 容量与放置分析”的组件表，至少记录容量、已用、空闲和所属层；只看总 E2E 不能说明是哪一部分 KV 发生了移动。

## 6. 用 KV Cache 分层扫描直接找候选甜点

前端顶部新增“KV Cache 分层扫描”按钮。它会复制当前模型、当前负载和当前硬件，自动构造并逐一运行以下候选：

- **当前策略**：保留映射页现有的 KV 策略，作为同一场景的基线；
- **HBM（hbm0）**：固定在第一个 HBM，关闭卸载；
- **HBF（hbf0）**：固定在第一个 HBF；本次 B200 预设可以直接运行，参数仍标记为 analytical/user-configured；
- **混合（HBM + HBF）**：HBM 做活动缓存，HBF 后备容量按 `offload_ratio=1.0` 开放，容量压力下将页卸载到 HBF；如果自定义 HBF 缺少 active-memory 证据，会显示为不可行。当前 HBM 容量足够时没有迁移是预期结果，不代表混合策略没有生效。

操作步骤：

1. 先完成模型、硬件和负载设置；扫描范围会显示在窗口顶部的“当前模型 · 当前负载 · 当前硬件”。
2. 点击顶部“KV Cache 分层扫描”。
3. 点击“运行分层对比”，等待候选依次完成；扫描期间不要修改当前场景。
4. 在表格中比较候选状态、TTFT p50、TPOT p50、E2E p50、KV 峰值/容量、KV 流量和迁移/解释。
5. 窗口摘要会显示可比较候选数量和按 E2E 最低值标记的“E2E 最优”；它是当前模型和负载下的指标优胜者，不自动等同系统级最优。

扫描不会修改当前场景；关闭窗口后仍可按原策略运行。候选由当前后端逐场景调用 `/api/run`，因此每一行都包含完整事件仿真结果，而不是只用一个带宽除法估算。HBF 参数采用本次明确登记的分析坐标；如果换成缺少写入证据的自定义 Profile，HBF 的不可行状态仍是有效结果。

建议先用扫描得到三行结果，再选中一个候选回到“映射”页手工设定并运行一次，以便进入“结果”和“回放”页查看完整资源利用率、关键路径和迁移事件。

## 7. 校验、估算和运行

1. 点击顶部“校验”。
2. 若有错误，打开“诊断面板”，按组件、链路、Profile、KV 目标和控制平面目标逐项修正。常见错误是 HBF 不可写、KV 目标不可达、容量不足、Profile 缺字段或旧 Rank 映射引用已替换的组件。
3. 校验通过后点击“运行仿真”。前端会先打开“运行规模估算（Run Estimate）”，显示任务数、预计批次、风险等级和警告。
4. 点击“开始后台仿真（Start）”。后台任务窗口可以关闭，仿真仍继续；需要查看进度时点击顶部运行状态或“查看运行进度”。
5. 仿真完成后，页面自动进入“结果”。如果在运行期间改过场景，结果会标记为过期；请重新校验并运行当前版本。

结果报告中的每个数值都有自己的单位和语义。页面上显示 `ANALYTICAL` 时，应向老师说明这是离散事件/控制平面分析结果，不是芯片后测采样。

## 8. 结果页如何回答“哪种 KV 更好”

### 延迟和吞吐

结果页的“请求明细”表直接给出每个请求的：

- **TTFT**：从请求进入引擎边界到第一个可见 Token 的时间，重点看 Prefill 和初始 KV 建立。
- **TBT p50 / p95**：相邻输出 Token 的时间分布。
- **TPOT**：平均每个输出 Token 的时间，重点看 Decode 阶段的 KV 读取、批次竞争和调度。
- **E2E**：整个请求完成时间。

“推理运行时”区域还会显示批次数、峰值批次、抢占次数、Goodput、请求率和 Token 率。只改变 KV 策略时，模型、负载、调度和随机种子必须完全相同，才能把差异归因到驻留策略。

### KV 流量和迁移

在“推理运行时”展开以下两个分组：

- **KV 读写流量**：Prefill Read / Write、Decode Read、Decode Append，分别显示逻辑字节和物理字节。
- **KV 迁移与限制**：Offload、Prefetch、Migration、Recompute、Swap Transfer、Prefetch Distance。

解释时要区分：KV Read/Write 是注意力相关的逻辑/物理读写；Offload/Prefetch/Migration 是页移动；Recompute 是用额外计算换取较少驻留；Swap Transfer 是搬移时间。它们不能简单相加。

页面底部的“KV 容量与放置分析”显示：驻留模式、Split 模式、统一 KV、有效物理容量、瓶颈组件，并按组件给出容量、已用、空闲和所属层。这个表是回答“HBF 是否真的承接了 KV”的主要证据。

### 资源瓶颈和图表

- **资源利用率**：看 GPU Tensor Core、HBM fabric、HBF/DMA、链路和 CPU 控制面是否达到瓶颈。
- **类别时间 / 关键路径**：判断时间主要落在 Compute、Memory、Communication、Synchronization、Policy 还是 Output。
- **组件与 Rank 性能时序**：点击“添加图表”可增加最多 4 张图；选择组件、Rank 和指标观察利用率或活动曲线。连续批处理曲线是批次包络/聚合语义，页面会显示 fidelity，不要把它当作硬件采样。

建议每个 KV 方案至少保存三张截图：请求指标、KV 容量与放置分析、KV 迁移与资源瓶颈。

## 9. 回放页如何展示“KV 发生在哪里”

点击左侧“回放”，仿真后会生成确定性 Trace：

1. 使用“播放”“上一步”“下一步”和时间滑条定位 Prefill、Decode、KV read/write、Offload、Prefetch、Migration 和同步阶段。
2. 用请求、批次和逻辑 Rank 下拉筛选，减少老师现场看到的事件数量。
3. 点击数据流拓扑里的节点或链路，右侧“选中事件”会显示计算主体、数据流、时间、并发和精确标识。
4. 展开“语义事件流”，按关键词、类别、阶段和时间状态筛选；每页最多 50 条。
5. 点击“复制诊断信息”可以把当前事件详情复制到讲解记录中。

回放只表达仿真事件、逻辑内存区间、协议路径和 Rank 算子，不伪装成 JEDEC bank/row 级模拟。它适合展示因果路径，结果页适合展示汇总数字。

## 10. 候选扫描、基线比较和 Native 评分

### 架构候选扫描

在“架构”页点击“候选扫描（Scan）”：

- 选择 `自动`、`NumPy CPU` 或可用的 `CuPy CUDA` 批量后端。
- 设置“返回候选数（Top N）”，点击“扫描当前架构”。
- 结果表显示算子、执行组件、逻辑 Rank、局部 `M × K × N`、瓶颈和估算耗时。

候选扫描是基于代表性 GEMM 的 Roofline 分析，不是完整事件仿真，也不是自动部署计划。可以用它解释为什么某个硬件候选在计算侧更好，但 KV 结论仍以完整场景运行结果为准。

### GPU 基线比较

在“结果”页点击“与 GPU 基线比较”，它会把当前场景和纯 GPU 放置的候选作一次对比，显示候选/基线的 makespan、延迟速比、吞吐速比和能耗比。它回答的是“当前拓扑相对 GPU-only 的变化”，不替代 HBM/HBF 三方案矩阵。

### Native 评分

顶部“Native 评分”用于当前场景与已保存 Native 参考 JSON 的直接对比。对比前要保证参考数据与模型、Prompt/Output、并发和运行时边界一致；R0 JSON 是独立参考，不能覆盖或重新写入。评分结果会在结果页显示 Native 指标和 R0 对照，适合作为校准证据，不适合把未校准 HBF 方案包装成实测结论。

## 11. 现场甜点扫描的最小协议

为了找到不同模型和负载的最佳 KV 点位，建议把扫描拆成两层，避免把变量混在一起：

1. 固定硬件、模型、量化、TP/PP/EP、页大小和调度策略。
2. 固定一组负载，例如 `personal_assistant`。
3. 点击顶部“KV Cache 分层扫描”，先让当前前端自动运行当前策略、HBM、HBF 和混合候选；记录每一行的 TTFT p50、TPOT p50、E2E p50、KV 峰值/容量、KV 流量和迁移解释。
4. 对扫描中状态为“可比较”的方案，回到“映射”页逐一固定策略再运行一次，记录 Token/s、资源利用率、关键路径、Offload/Prefetch/Migration、Swap Transfer 和瓶颈组件。
5. 对同一模型换 `customer_service`（短输出高并发）和 `content_creation`（长输出）重复步骤 2–4。
6. 再换模型，优先选择结构明确且支持级别为 `exact` 的模型；模型预设或支持级别改变时，重新保存场景和证据。
7. 把结果表中同时满足延迟目标、容量不溢出、迁移可接受、吞吐较高的候选标为“甜点区”。只有当参数来源和事件语义满足要求时，才称为可用于设计决策的候选，不把单个最小 E2E 点称为普适最优。

推荐现场表格：

| 模型 | 负载预设 | KV 方案 | TTFT | TPOT | E2E | Token/s | KV 峰值 | Migration / Swap | 瓶颈 | 证据级别 |
|---|---|---|---:|---:|---:|---:|---:|---:|---|---|
| Qwen… | personal_assistant | HBM-only |  |  |  |  |  |  |  |  |
| Qwen… | personal_assistant | HBM→HBF |  |  |  |  |  |  |  |  |
| Qwen… | personal_assistant | 按 layer 混合 |  |  |  |  |  |  |  |  |

“最佳”至少要有一个约束：TTFT/TPOT/E2E 的 SLO、最大容量、可接受迁移时间或吞吐目标。没有约束时只能说“该指标下最低”，不能说系统级最优。

## 12. 导出、复现和截图

每个方案运行完成后，按以下顺序保存：

1. 点击“导出 JSON”，保存完整场景，例如 `qwen25_personal_hbm_only.json`。
2. 点击“导出硬件参数”，保存独立硬件输入，便于下一台机器复用同一拓扑。
3. 点击“导出标准 IR”，保存校验通过后的 Canonical IR，作为结构复核材料。
4. 在结果页展开“运行技术详情”，截图运行 ID、Schema、模拟器版本、模型、硬件、负载、证据等级和假设。
5. 截图“请求明细”“KV 容量与放置分析”“KV 读写流量 / KV 迁移与限制”以及回放页的关键事件。
6. 复制“诊断信息”或保存浏览器下载的 JSON；文件名中写入模型、负载和 KV 方案，不要用 `result.json` 这种会互相覆盖的名字。

重新载入方案时，优先“导入 JSON”；只想替换硬件时使用“导入硬件参数”。导入后仍要点击“校验”，因为硬件组件 ID 变化会使旧 Rank、KV 和控制平面目标失效。

## 13. 5 分钟备用演示

如果现场时间很短，使用以下路径：

1. “载入参考”确认页面可运行。
2. “硬件预设库”载入 `nvidia-b200-1gpu-2hbf-2hbm`。
3. “模型预设”选一个 `exact` 的 Qwen 或 Llama 类模型。
4. “负载”选 `personal_assistant`。
5. 点击顶部“KV Cache 分层扫描”，运行当前策略、HBM、HBF 和混合候选；展示表格中的 TTFT、TPOT、E2E、KV 峰值/容量和不可行原因。
6. 选一个可比较的候选，在“映射”页固定该策略，点击“校验”后“运行仿真”；截图结果中的 TTFT、TPOT、E2E 和 KV 峰值。
7. 最后点“回放”，定位一次 Decode KV read 或 Migration 事件，说明结果数字和硬件路径是同一份仿真报告的两个视图。

如果换用了没有 active-memory 写入字段的自定义 HBF Profile，不要绕过校验强行选成 KV；改为展示 HBF 的权重/冷数据后备路径，并说明该 Profile 的写入证据不足。默认 B200 演示预设已经带有本次指定的 active-memory 分析参数，但仍不能把它称为芯片实测。
