先认识 10 个词

TTFT / TPOT
请求到达后多久出第一个 token / 之后平均每个 token 的生成间隔。
KV 缓存
注意力层为每个请求保存的历史键值，随生成变长，占显存。
Prefill / Decode · PD 分离
先一次处理整段提示词，再逐 token 生成；PD 分离是把两步放到不同机器上。
TP / PP / EP
张量并行 / 流水线并行 / 专家并行：把一个模型切到多张卡上的三种方式。
profile（性能画像）
在真机上实测好的算子耗时表，仿真时查表或插值。
HBM
GPU 旁边堆叠的 DRAM 显存，按 bank 和行组织。
HBF
用 NAND 闪存堆叠成的高带宽存储，容量大，但写入（编程）慢。
tRCD
HBM 用 ACT 命令打开一行后，要等这么久才能读写；PRE 命令关闭该行。
tPROG
NAND 写入（编程）一页所需的时间，远长于读一页。
FTL / GC
闪存的地址映射层 / 垃圾回收：回收时要把有效页搬走再擦除整块。
1

先看结论：按要研究的问题选工具

没有一个工具能回答所有问题。先确定问题落在哪一层：服务调度、硬件设计，还是内存器件；再选在这一层真正建了模的工具。

问题
要预测 TTFT / TPOT，挑部署配置
AISimulate · Vidur · LLMServingSim 2.0
请求、组批、KV 容量和排队都在模型里；器件快慢来自实测数据，换新硬件要重新测。
问题
要研究 HBM 行命令、刷新与时序
Ramulator 2.1 · DRAMsim3
逐条模拟 DRAM 命令，但只算内存请求何时完成，没有 LLM 请求；要看到 TTFT / TPOT 的变化，需要接跨层前端，如本项目 HeteroLLM-sim。
问题
要研究 HBF 写入、GC 与寿命
HBFSim（FlashLabAE）· MQSim
页编程、擦除、地址映射、GC 和磨损都会计时。MQSim 走 SSD 接口，不等于 GPU 直连的 HBF；想在真实 GPU 上看注入效应，用 SlugLab 版 HBFSim。
问题
要比较算力、带宽、拓扑设计
LLMCompass · GenZ · ASTRA-sim · SimAI
计算阵列、片上缓冲、Roofline（算力 / 带宽上限估算）和集合通信；不模拟内存器件时序。

本项目的位置HeteroLLM-sim 把服务调度、多卡并行和 HBM / HBF 器件时序放在同一条时间线上，覆盖面最宽；但还没有统一的实机误差，HBM 只覆盖正常操作子集，HBF 也没有 FTL / GC（见第 3、5、6 节）。

判断标准：改一个参数，结果变不变

功能清单很容易写满，所以这页不按“有没有提到某功能”打分，只问一件事：把这个机制的参数改大，仿真结果会不会跟着变。同样是“算了 HBM”，两个工具的做法可以完全不同：

Vidur服务仿真器
HBM 时间从哪来真机实测的算子耗时HBM 的影响已经包含在测量值里
把 tRCD 调大
结果✕ 不变没有任何计算读取 tRCD；只有重测 profile 才会变
Ramulator 2.1DRAM 仿真器
HBM 时间从哪来逐条模拟 ACT → RD 等命令每条命令都要满足时序间隔
把 tRCD 调大
结果● 会变开行到读写的间隔变长，没命中已开行的访问和排队都会变慢

所以，Vidur 并没有“忽略内存”，它只是把内存的影响折进了实测数字里，底层参数传不进去。下面的总表只把后一种情况记为“支持”；对前一种，第 4 节会说明它的内存时间到底从哪来。

3

能力总表：同一把尺子量 14 个工具

10 个机制分成三组，每格都按第 2 节的标准判断。悬停或用 Tab 键聚焦任一格，可以看到判断依据。

服务调度

连续批处理：请求一结束，空位马上由新请求补上，批的组成随之改变。

KV 容量：KV 缓存随生成增长、结束后释放；装不下时，新请求要等待或被抢占。

PD 分离：KV 从 Prefill 机读出、经链路传输、写入 Decode 机，三段都要计时。

多卡并行与互联

TP / PP / EP：模型按张量、流水段、专家切到多张卡，切法要进入计算和通信时间。

链路争用：多路数据同时走同一条链路时，要排队分带宽，而不是各按满带宽算。

内存器件

HBM 命令：逐条模拟开行、读写、关行和刷新，行命中与否改变时延。

NAND 时序：HBF 的页读、页编程、块擦除各自占用闪存阵列。

FTL / GC：垃圾回收搬运有效页产生的读写也要计时。

●支持：已实现并核实 ◐部分：有这条路径，缺关键环节 ✕不提供：属于它的研究范围，但没有这个机制 ?待核实：公开材料不足，不算劣势 —不适用：不在它的设计范围内

✕ 和 — 的区别：✕ 是该做而没做，例如 HBF 仿真器没有 FTL / GC；— 是本来就不做，例如服务仿真器不模拟器件，DRAM 仿真器不处理 LLM 请求。服务类工具的器件列多是 —，但它们的结果里照样有内存时间，见下一节。

4

✕ 和 — 不等于没算：内存时间藏在哪

用两个器件参数做探针：HBM 的 tRCD（开行后到能读写的等待）和 NAND 的 tPROG（写一页的时间）。每个工具看两件事：这部分时间从哪来，只改这一个参数结果会怎样。

● 会变参数进入时间线 ◐ 有条件只在特定后端或路径上进入 ✕ 不变没有入口，只能改更高层参数或另接模型 ? 待核实 — 不适用
工具HBM 时间从哪来只改 tRCDNAND 时间从哪来只改 tPROG

结果“不变”的工具想研究新器件，只能改更高层的有效参数（带宽、时延、profile），或另接一个器件模型。例如把聚合存储层的带宽设成 HBF 的数值，并不会凭空产生页编程或擦除。

容易混淆的地方

下面这几处最常被读错，引用表中结论前先核对。

两个同名的 HBFSim

FlashLabAE/HBFSim 是事件驱动的系统模型，SlugLab/HBFSim 在真实 GPU 上插桩注入，二者是独立项目，能力、论文和精度数字不能合并。另有一篇 HBF-Sim 论文（Accel-Sim 扩展），本轮未确认公开仓库和许可证，没有列入。

精度数字不能横着比

算子误差、请求延迟误差、命令合法性、延迟注入误差和训练一致性，回答的是不同问题；本次也没有跑统一基准。另外，“支持某种配置”和“该配置的精度已验证”是两种不同的证据。

公开基线 ≠ 论文扩展

Exploring HBF 论文用的是扩展版 LLMSimulator（增加了 HBF、PD 导入、连续满批和部署搜索），扩展版仓库本轮未确认，表中只按公开基线评。ASTRA-sim 同理：按公开 2.x 主干评，3.0 论文的初始补丁（PR #389）核查时仍开放。

名称与版本

AISimulate 是 AIConfigurator 的继任项目，发行名正迁移为 aisim。LLMServingSim 按当前 2.0 主干（vLLM 层级 profile + ASTRA-Sim 解析网络）评，2024 版基于 ONNXim 的描述已不代表现状。SimAI 当前版本含推理，不只是训练仿真器。

本项目的边界

HeteroLLM-sim 的 HBF 当前没有 FTL / GC；HBM 只覆盖正常操作子集（初始化、低功耗、训练、ECC / RAS 未建模），不是完整的 JEDEC 控制器。研究报告里的 10% 是条件预测预算，不是“实机误差 ≤ 10%”。

仿真速度 ≠ 被仿真系统的性能

仿真器跑完一次要多少分钟，和它算出来的 TTFT / 吞吐是两回事。各论文的工作负载、硬件、版本和保真度都不同，本次不按分钟数或加速比给仿真速度排名。
