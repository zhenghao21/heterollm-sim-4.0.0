# Graph 收益预测局限：0.6B 与 1.7B

这四组最终仿真确实执行了普通 CUDA 提交和 Graph 生命周期成本，但**没有预测出 native 实测中的 Graph 加速**。本次只读审计未发现成本遗漏挂载或异步依赖接线错误；记录中的耗时变化可以由现有任务路径完整解释。此结论只覆盖以下两个模型，不能外推至其余模型或其他硬件。

所有数值来自已完成的前端任务及其原始报告；没有重新运行模型、修改参数或依据 native 误差调参。复核数据见 [graph_host_cost_path_audit.json](graph_host_cost_path_audit.json)，约 19 KB，保留原始浮点数、125 次稳定 decode 的逐次差值及原始报告路径，不包含节点图或重复的大段结构。

## 成本参与了执行，服务量不等于关键路径耗时

源码中，普通模式把 CPU enqueue 任务彼此串联，每个 GPU launch 依赖对应的 CPU 提交完成，CPU 不必等待上一 GPU kernel 完成。Graph 模式串联该次生命周期事件，GPU launch 依赖最后一个事件完成。两者保留原有设备任务需求。任务转换到在线阶段后仍保留资源和依赖；四组正式请求的 128 个 cohort 均使用 `resource_dag` 调度。

正式请求内的资源服务量如下。它们可能重叠，不能直接相加为请求总耗时。

| 模型 | 关闭时 CPU API 服务量（ns） | 开启时 CPU API 服务量（ns） | 两种模式相同的 GPU frontend 服务量（ns） |
| --- | ---: | ---: | ---: |
| 0.6B | 77480199.99999978 | 2573199.9999999823 | 79160000.0 |
| 1.7B | 108431999.99999914 | 2731199.9999999856 | 75520000.0 |

例如，1.7B 稳定 decode 的普通 CPU 提交为约 842.1µs，Graph replay 为 1.7µs；同时，两侧仍有 590µs 的 GPU frontend 服务和约 3529.879µs 的 device-stream body 服务。普通 CPU 提交的大部分服务被设备工作重叠，因此减少约 840µs 的 CPU 服务并没有带来等量的请求加速。阶段的 `component_id=gpu0` 是分组标签，组内 CUDA host 任务仍使用 `cpu0.cuda_submission`，没有变成 GPU 服务或被删除。

## 请求差值的精确分解

下表均为 **Graph 开启 − 关闭**，单位 ns。两个模型的正式请求在 prefill 和第一个 decode 直接执行；第二个 decode 发生销毁旧图、捕获、更新及重放；随后 125 个 decode 稳定重放。

| 差值来源 | 0.6B | 1.7B |

| 首 token | 0.0 | 0.0 |
| 第一个 decode | 0.0 | 0.0 |
| 第二个 decode（重新捕获） | 139333.49514567852 | 189258.1355934143 |
| 125 次稳定 decode 合计 | 91686.89318621159 | -42733.05082321167 |
| 以上分解之和 | 231020.3883318901 | 146525.08477020264 |
| 实际请求总耗时差 | 231020.3883318901 | 146525.08477020264 |
| 分解残差 | 0.0 | 0.0 |

1.7B 每次稳定重放减少 `341.86440658569336 ns`。0.6B 每次稳定重放增加 `733.4951325654984` 至 `733.4951456785202 ns`；其普通提交总成本等分到 618 个 modeled launch 后约为 `966.5048543689294 ns`，小于 1700ns 的 Graph replay。这里的微小差别是当前合成 API 成本和依赖调度的结果，不代表真实 GPU 的收益。

两模型 Graph 开启时的正式生命周期事件数相同：`ordinary_submit=2`、`destroy_graph=1`、`capture=1`、`update=1`、`replay_submit=126`。其中一次重放属于重新捕获调用，其余 125 次为稳定重放；关闭时为 `ordinary_submit=128`。

## 解释边界

当前实验改变的是 host 生命周期/API 成本，仍保留每 kernel 的分析 launch 参数和设备物理成本。Graph 设备调度收益缺少独立校准，合成小 kernel 的 host API 成本也未证明能准确代表真实模型 kernel。它们是解释预测偏差的建模局限，**本次没有独立量化各项分别造成多少误差**。不得从上述 native 差值反推补偿系数，也不能将分解残差为零理解为预测精度合格。

报告中的 `cpu_gpu_overlap_ns=0` 也不能证明同批次内没有 CPU/GPU 重叠：现有字段计算的是当前 host 阶段与**上一批 GPU 区间**的重叠，没有统计同批 CUDA API 任务与 GPU kernel 的交集。`gpu_idle_waiting_for_host_ns` 同样是阶段边界指标。这是指标范围限制，不是上述请求耗时差的来源。

本次未通过逐任务重放重新生成时间线；以上结论基于完成报告中的实际资源服务量、逐批阶段时间和源码依赖检查。其余模型必须依据各自最终结果另行分析。
