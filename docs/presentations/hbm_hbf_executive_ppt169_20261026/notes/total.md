# 1_仓库比喻与建模总流程

可以先把两种存储理解为两种取货方式。HBM 的一个 bank 像柜子，row 像抽屉；柜子同时保持一行打开，读请求在该行中按小块传数据。HBF 的一页像整箱物品，读取先付整页的介质服务，再通过内部通道搬到临时读缓冲，最后送到出口。每个 plane 有两个读缓冲槽，类似两个临时装卸位。这里的柜子和货架只是帮助理解，图中大小和数量不表示实际容量或速度。

仿真过程先由模型、批量、上下文、精度和并行配置确定权重、KV 与激活的访问需求，再结合放置和分配器得到 owner、字节数和地址。物理 Core 在任务实际到达时计算服务与资源等待，完成事件推进后继任务，最终影响 Token 吞吐与延迟。因此，地址决定去哪个资源，状态和竞争决定何时完成。源码入口为 src/heterollm_sim/planner.py:8975、16306、19067，data_motion.py:1151、1330–1496，memory_mapping.py:172、212。

# 2_HBM行状态与命令链

HBM 的关键不是只知道传了多少字节，还要知道目标行是否已经打开。本项目的 jedec_hbm 路径把请求拆成三十二字节 burst，再按地址映射到 channel、pseudo-channel，也就是 PC，以及 bank 和 row。行命中时直接发 RD，经过读流水延迟 RL，再进行 DQ 数据传输。bank 关闭时，要先 ACT 开行，等待 tRCD，再读。行冲突时，先 PRE 关闭旧行，等 tRP，再 ACT 打开新行，因此多付开关行和等待成本。图只表示顺序，不按时间比例，也省略 ACT 在具体时钟边沿上的精细锚点。

这些命令还需要满足 tCCD 列间隔、tRRD 与四激活窗口 tFAW、读写方向切换和刷新约束，写对应 WR 与 WL。请求完成取所有 burst 数据结束时间最大值，完整延迟含到达之后的等待。analytical 是另一种简化模式，不应把本页当成所有模式共同的精度承诺。源码是 src/heterollm_sim/memory_mapping.py:18、47、172，_hbm_control.py:121、145、183、206、279、490、547、584，以及 dram_core.py:90、483。

# 3_HBF页服务与双缓冲

论文原生 HBF 例子每堆十六个 die，每 die 二十五个 plane，四 KiB 页。连续页先条带到 die 内部通道，再轮到不同 plane，几何决定可并行的阵列资源。把未命中读分成三步看：先从页阵列读一整页，数据留在该 plane 的介质暂存；再占用 die 内部通道，将页搬到选中的读缓存槽；最后通过 host 出口送给请求方。介质暂存和两个读缓存槽是不同层次，不能合并。图中棕橙主线表示新页 B 的路径，灰色虚线表示已有页 A 命中时从缓存槽出发的旁路；这是路径示意，不是同一瞬间的硬件快照。

每槽记录页标识、ready 和 reader_end。填充完成前不能读取，旧读者结束前不能覆盖。缓存命中绕过阵列读取和内部填充，但仍需等 ready 和出口资源，不代表立即返回。写操作单独走 host、内部传输、program，program 结束才算完成；部分页写按配置拒绝或另付读改写成本。本例读一微秒、program 一百微秒是配置输入，本次没有新增性能测量。当前基线为 generic_nand，直接地址页服务，无默认 FTL、垃圾回收或自动擦除，也没有自主预测预取控制器。源码为 scripts/exploring_hbf_paper_config.py:153、272–342，src/heterollm_sim/memory_mapping.py:124、212，nand_core.py:647、666、1861、1900–1982。

# 4_资源时间线与排队

时间线的前提是 generic_nand 读服务：A 和 B 是映射到同一 plane 的两个不同未命中页，请求已准入，没有写暂存覆盖，两个读槽初始为空。灰色代表 A，棕橙代表 B。每页先阵列读取，再内部填槽，最后 host 输出，这是实线连接的同页依赖。虚线强调另一条约束：A 的内部搬运结束、介质暂存释放后，才允许同 plane 的 B 开始阵列读。因此，读 B 不能与填 A 重叠，但可以与输出 A 重叠。B 用另一个槽，所以填 B 也可与输出 A 重叠。

同一内部通道和同一 host 读出口都不能同时服务两次传输，输出 B 必须等自身填充结束并等 host 空闲。图中的下方括线表示出口 A/B 不能重叠。若下一页需要覆盖槽 A，新的内部填槽还必须等槽 A 的最晚旧读者结束；阵列读本身可以先结束，数据在介质暂存中等候，这段等待也会阻止同 plane 再读下一页。host 输出结束不会自动清空缓存页，只解除覆盖约束，所以该页以后仍可能命中。图的长短没有数值比例，也不保证理想流水。源码为 src/heterollm_sim/nand_core.py:1817–1819、1901–1956、647–665，以及 memory_transfer.py:263–335。

# 5_指标输出与性能归因

模型除了给 Token 指标，还保留能解释性能的物理观测。HBM 有行命中、冲突和 ACT、PRE、RD、WR、REF 命令；HBF 有缓存命中、实际读页和 program。两者输出完成时间、逻辑和物理字节、队列等待和各资源 busy。任务依赖再把这些结果连接到 Token 吞吐、首 Token 延迟 TTFT 和平均输出间隔 TPOT。TPOT 等于首末可见 Token 之间的时间除以输出数量减一，属于平均值。比较配置要固定负载并保持统计边界一致，不能把访问模式变化误认为介质本身性能变化。

三个时间口径必须分开：service_ns 累加任务和 owner 的服务跨度，跨度可能重叠；resource_totals 描述资源忙碌；makespan 是整体完成窗口。它们不能互相替代。配置还区分标准参考、论文输入和本地研究假设。例如论文原生 HBM4 的 tRRD 与 tFAW 借用 HBM3E 参考；NAND 的块几何、erase、内部带宽等含显式本地选择。因此结果可用于机制分析和配置比较，尚未经目标芯片实测校准。源码是 src/heterollm_sim/memory_types.py:899、911，memory_service.py:26–84，reporting.py:632、2113、2174–2246，以及 scripts/exploring_hbf_paper_config.py:207–258。
