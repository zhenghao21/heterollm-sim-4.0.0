Inside the memory model

一笔 HBM 访问，
如何变成时间与成本。

以当前工作区实现为准，从请求地址到资源时间线逐步拆解。点击章节、切换例子、播放访问过程；所有数值都标明所属模型与假设。

HBM 的身份是配置，执行器是共享 DRAM 核心。

HBM、DDR、LPDDR、GDDR 复用 DramConfig → DramCore。差别由几何结构、带宽、时序、资源连接与上层访问模式表达。它是轻量物理事务模型，不是逐周期 JEDEC 控制器仿真。

01
示例：GPU kernel 读取一块权重；逐步点击也可查看。

有实际地址，才能谈行命中

正式物理执行使用 buffer 分配、偏移与 owner（所属内存节点）确定地址。连续字节是一个请求；离散访问要表达成多个请求。

两个模式，不能叠加计时

默认 physical 在事件到达时提交 DRAM 核心；显式 aggregate 使用汇总公式。规划阶段的估算不是第二笔内存耗时。

“成本”首先指资源消耗

主后端记录纳秒、物理传输字节和资源占用。采购价 / TCO 是独立研究脚本的假设模型，不会自动进入 HBM 时序。

逻辑字节是想要的数据；物理字节是实际搬动的块。

物理核心按 burst_bytes 向两端覆盖，再把每个 burst 映射到 lane、bank、row、column。下例固定 64 B burst；彩色部分是有效数据，整格是被访问的块。

02
N = floor((address + bytes − 1) / burst) − floor(address / burst) + 1
physical_bytes = N × burst_bytes

部分写同样按整 burst 计写流量；DRAM 核心不额外模拟 NAND 式的读改写。若启用写分配缓存，缓存层可能先读一条 cache line，那是另一层规则。

当前 HBM 预设的地址条带

16 lane × 每 lane 16 bank；row = 8192 B；interleave = burst = 64 B。lane 是共享数据通道的编号。

为什么连续地址未必是同一 bank？

默认先轮转 lane，再轮转 bank，随后推进该 bank 内的列和行。因此地址 0 与 64 落在不同 lane；0 与 16,384 才是同 lane、同 bank 的下一列。

q = floor(address / 64)
lane = q mod 16
bank = floor(q / 16) mod 16
u = floor(q / 256)
column = u mod 128
row = floor(u / 128)

本公式用于单 stack、单 die、64 B 交织的当前示例。通用实现还先解码 stack/die，并支持更大 interleave；column 的单位是 burst 索引，不是字节。

延迟决定何时出数据，带宽决定搬多久。

每一段时间从哪里来？

command_start = max(开行依赖, 命令资源可用时刻)
data_ready = command_start + 读/写延迟
data_start = max(data_ready, 上次数据结束 + 切换间隔)
data_end = data_start + burst_bytes / 该方向单 lane 带宽

命令延迟从 command_start 计算，不从 command_end 计算。切换间隔仅在读写方向变化时非零，已有空闲可吸收它。读写共用同一条 lane 数据通路；不同 lane 的数据通路可重叠。

完成时间和资源占用不是同一个量

读请求完成于最后一段数据末尾；写请求还包含写恢复。恢复约束未来换行，不阻止同一打开行继续发列命令。流水等待只作延迟标注，不算命令资源忙碌。

稳态单 lane 吞吐 ≤ min(单 lane 方向带宽, burst / 命令间隔)
批次有效带宽 = 总逻辑字节 / (最晚完成 − 最早到达)

各资源忙碌时间可以重叠，不能简单相加当成总延迟。共享一个命令口时，所有 lane 合计还受 burst / 命令间隔限制。增加在途窗口只放宽接纳；queue_wait_ns 仅指接纳等待，不包含 bank / 命令 / 数据总线等待。

先认清“账单”：时间与字节分别记录。

物理模式的正式时间来自事件运行时；下方计算器专门展示 HBMProfile.memory_service 的汇总模型。两条路径各有口径，不应串起来重复收费。

04

物理模式：按最终访问记一次

例：地址 48 读 32 B，64 B burst → 实际读两个 burst，共 128 B。

逻辑读取 32 B → 覆盖 2 个 burst → 物理传输 128 B

仅替换本 HBM 对应的旧 backing demand（后备内存需求），保留计算、L2 缓存和独立链路开销。按物理 resource_id 维护资源占用；如果外层资源与物理通路是同一条线，不重复收取。

L2 全命中时，HBM 访问可归零，但 L2 本身仍有服务时间。跨介质搬运通常有源端读、链路传输、目的端写三类实际工作。

算子总账：同阶段取最大，顺序阶段再相加

无资源竞争时，CostPhase 内可并行的资源需求时间取 max，CostEstimate 内顺序阶段的时间取 sum。

启动 2 μs + max(计算 8 μs, HBM 12 μs) = 14 μs

这是成本模型的服务需求，正式事件执行还受队列和资源竞争影响。全局 bytes_moved 会累加缓存、HBM、链路等多层，不能全部当成 HBM 流量。相同物理字节的行命中与行冲突可能产生不同延迟。

汇总计费计算器：同一笔读写，三种 service_model

默认示例：读 300 B + 写 100 B、读写 40 ns、交易块 256 B、32 个在途槽。此处知道流量，不知道实际地址、行命中或访问顺序。

三种公式与适用范围
T_BW = R_p / B_read + W_p / B_write
N_r = ceil(read_bytes / 256)
N_w = ceil(write_bytes / 256)
W = min(Q × parallel_lanes, N_r + N_w)

R_p / W_p 是本模式的计费物理字节；serialized / overlapped 各方向先补齐到256 B，analytical保留原payload。读写共享控制器，方向带宽时间相加。若两个方向速率相同，代码用总字节 / 带宽保持浮点运算顺序。这里输入的是最终有效带宽；profile 通常先乘 efficiency，显式 measured_effective_bandwidth 则直接使用。

analytical：不补齐字节
T_L = max(活跃方向单请求延迟, (N_rL_r + N_wL_w) / W)
T = max(T_BW, T_L)

serialized / overlapped：各方向补齐到 256 B
T_L = ceil(N_r / QL) × L_r + ceil(N_w / QL) × L_w
serialized：T_BW + T_L；overlapped：max(T_BW, T_L)

零流量返回 0；QL 表示 Q × parallel_lanes。汇总模型的并发约束是乐观下界，不等于物理队列等待。这里的交易块 256 B 与物理 DRAM 的 64 B burst 是两个参数。

为什么 cost profile 又写着 40 ns？

组件同时附带 legacy / aggregate HBMProfile：40 ns、256 B transaction、32 outstanding、parallel_lanes=1。正式物理配置却为35 ns、64 B burst、64 outstanding、16 lane。它们作用于不同路径；physical 模式不会把两者延迟相加。

改参数前，先看它改变什么

参数 / 单位生效方式一个容易误判的例子
data_lanes / lane 数显式值优先，否则 channels × subchannels × pseudo_channels。stacks、dies 不参与 lane 数乘法；多一层 die 不会自动增加外部带宽。
interface_bandwidth_gb_s总接口带宽除以 lane 数，得到单 lane 带宽；不可同时设 lane_bandwidth。总带宽固定，lane 数翻倍：每 lane 分到的带宽减半。
lane_bandwidth_gb_s直接给单 lane；总带宽 = 单 lane × lane 数。两种输入都未指定时，用 data_width_bits × MT/s / 8 / 1000。
read/write_bandwidth_gb_s方向总带宽上限，分别除以 lane 数。不得超过物理接口峰值。读 100 GB/s、写 50 GB/s 同一数据资源仍串行占用，不是两根独立线。
capacity_bytes默认由几何乘积计算；显式容量不超过几何容量，并与 burst 对齐。请求越界会报错，不自动循环地址或溢出到另一内存。

这些规则决定“为何两次看似相同的读写可能不同”，以及“哪些加速只是让模拟程序运行得更快”。

06

L2 缓存例子：冷读 → 热读 → 部分写 → 脏行逐出

假设启用显式 128 B cache line、write-back 与 write-allocate，buffer 中完整存在这条 line；最后访问新 line 造成容量不足，按 LRU（最近最少使用）逐出旧 line。点击步骤查看仅属于 HBM 的流量。

L2：无有效行→dirty = false→HBM 读 128 B

完整128 B line的冷写可免初始填充读，之后脏行逐出才写回。这里的“热”是 L2 命中。DRAM 的 row hit 只是 bank 内已有打开行，仍要传输数据；两者不要混淆。

RULE / 01

多请求按提交顺序接纳

原始到达相同、窗口 Q=1 时，第二个请求等第一个完成；Q=4 可更早进入，但同一命令 / 数据资源仍要排队。这里没有按行命中率优先重排的 FR-FCFS 控制器。

RULE / 02

共享命令，独立数据

shared_command_resource 使 pseudo-channel 或其他 lane 共用一个命令日历。例：两条 lane 可以并行搬数据，却只能按命令间隔依次发命令。是否共享由配置决定，不由 HBM 名称自动决定。

RULE / 03

恢复时间不等于总线一直忙

写数据在 30 ns 结束，write_recovery=15 ns，则该写请求到45 ns才完成，未来换行也受此约束。同一打开行仍可流水发列命令，数据线也不是自动占用到45 ns。

RULE / 04

同一 owner 的状态持续存在

运行时复用对应 owner 的核心、bank 状态和资源日历。例：第一次读留下 open row，第二次同 row 访问可以命中；不是每个 task 都重新生成空闲 HBM。不同 owner 的独立资源才可独立推进。未传运行时的 PhysicalService.price 是新的预览；便利函数 dram_service() 则每次新建核心，连续调用它不保留上一笔的打开行。

RULE / 05

大请求走摘要加速，语义仍相同

不捕获明细、映射与资源日历满足条件时，≥64 个 burst 的请求可进入编译数值路径；不适合时回退。多个请求也可批处理。这是模拟程序的加速，不是“HBM 突然加速”；不采样，仍处理行边界与切换，但浮点递推可能有一个 ULP（浮点数最小间距）的舍入差异。

RULE / 06

明细截断不截断真实流量

展开超过 max_expanded_segments 时，逐 burst 路径清掉明细并置 details_truncated；调度、物理字节与完成时间继续计算。例：图上没有完整 burst 列表，不代表只算了前面一部分。

RULE / 07

HBF 与 HBM 不共享介质内核

HBF 属 NAND 路径，有页、擦除、内部总线等规则。HBF 搬到 HBM 的例子应分别算源介质读取、拓扑链路和 HBM 写入；不能把 HBF 的页写放大、擦除或热磨损规则套到 HBM。

RULE / 08

这份模型没有承诺什么

DRAM 核心没有刷新事件、完整 JEDEC 时序约束、ECC 错误/重试、真实数据值、电气信号。调带宽可以表达降额假设，但不等于实现了这些机制。

稳定分配与重叠地址依赖

64 B 对齐下，A 分配100 B占据base=0，后分配B的base=128。再访问同一个 buffer + generation 会使用原地址；只有显式 alias 才能声明重叠。

同一任务内部：后读等待之前重叠写，后写等待之前重叠读/写；读读或互不重叠的地址不因此串行。例：先读[0,64)，再写[32,64)，后写必须等待前读；读[128,192)没有这一依赖，仍可能遇到资源竞争。

物理分配器不因一次普通访问自动搬迁已有buffer。时序实验室直接向core提交已独立的示例请求；不代替任务层的地址依赖解析。

预取到 HBM 后，还要再读它

例：16 KiB KV页从HBF预取到HBM：HBF源读 → 链路 → HBM目标写（256个64 B burst）→新位置可用。后续attention使用它，还要产生HBM读；“驻留HBM”不代表L2命中。

异步预取先完成源读，才推进链路与目标写，不会提前往有序物理日历提交未来写。若经host DRAM中转，还多出中转端写16 KiB与读16 KiB。

复制的具体重叠由执行模式决定，不能把所有路径都简化成固定延迟相加。service_ref仅指向同一内存服务时，连接边不另收一份相同服务费。同一存储、同一分配与偏移的alias COPY可归零。

硬性边界：AccessRequest / DRAM 核心只接受有效范围内、正长度的 READ/WRITE；ERASE 被拒绝。外层 price 的零字节请求可以直接返回零成本。正式组件必须提供完整的物理配置；不会因为名字叫 HBM 就悄悄补成某个产品默认值。
