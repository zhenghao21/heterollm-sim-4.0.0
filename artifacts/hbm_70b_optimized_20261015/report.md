# 70B 优化版本完整实验结果

完成日期：2026-10-16。`round2` 四点全部完成，执行检查和独立复核均通过；仿真进程已经正常退出，十分钟定时跟进已暂停。最终四点数据仅来自同一轮稳定实现。

## 实验条件

- Llama 3.1 70B，80 层，BF16 权重 141,104,775,168 字节（约 131.414 GiB）；使用模型结构仿真。
- 输入 128 token、批量 1、输出 4 token，即一次 prefill 和三次后续 decode。
- 同一套硬件库存：256 GiB 主机内存、512 GiB HBM、1 TiB HBF。A 的权重与 KV 均在 HBM；B 权重仍在 HBM，KV 在 HBF。
- reference 与 Ramulator2 对照只改变 17 项实际执行时序字段；几何、容量、时钟、带宽、调度和放置规则保持一致。

纯 decode 吞吐只统计首 token 后的三个 token；全过程吞吐包含 prefill 与初始化等待。这里 TPOT 是单个请求首末 token 之间的平均间隔。

## 参数与放置的影响

| 比较方向（后者作基准） | TTFT 变化 | TPOT 变化 | 纯 decode 吞吐变化 |
|---|---:|---:|---:|
| Ramulator2 相对 reference，A | +0.0380% | +5.1100% | -4.8616% |
| Ramulator2 相对 reference，B | +0.0187% | +4.8424% | -4.6188% |
| B 相对 A，reference | +2.4172% | +5.7843% | -5.4680% |
| B 相对 A，Ramulator2 | +2.3974% | +5.5149% | -5.2267% |

在本工作负载中，换成 Ramulator2 整组时序后，后续 token 延迟增加约 4.84%–5.11%，首 token 延迟变化很小。这是整组参数的影响，不能归因于某个单独参数。

将 KV 放到 HBF 后，后续 token 延迟增加约 5.51%–5.78%。此工作点的权重和 KV 已能放进 HBM，短上下文、批量 1 没有体现 HBF 容量扩展的价值；不能据此推广到长上下文、大批量或 HBM 容量不足的情形。

## 仿真速度与慢在哪里

最终采用上一轮已验证的行命中计算复用、请求常量外提、静态资源索引缓存、变化 bank/channel 写回及专用状态复制。Small 完整流程此前测得实际耗时减少约 23%–26%，完整返回结果相等，见 [性能对照](../hbm_execution_performance_20261015/report.md)。

本次 70B 的数值核心累计占单点实际耗时约 89.27%–89.71%。每个 cohort 都先执行独立成本计算，再执行正式持久运行时；四个 cohort 的两种执行均保留。正式 HBM 执行每点约 175 亿个 32 字节 burst，成本计算还需另行处理，因此几小时耗时主要来自命令量，监控未发现停滞。正式访存总量应读取 core_execution_audit，不能把监控中两阶段的字节直接视为正式流量。

第二轮调查中的 deadline 增量维护、历史时钟缓存、除法合并、ACT 起点复用均未采用。完整边界修复后的最后候选在真实 448 MiB 请求上慢约 4%–5%；撤回后以当前稳定版本重新运行四点，详见 [候选调查](../hbm_numeric_performance_round2/README.md)。

**没有测得 70B 完整流程的优化前后加速倍数。** 原八进程任务在运行约 191 分钟时停止，尚无完整大模型结果；它与本轮四进程也不具有相同并发条件。不能用旧任务未完成、局部微基准或 Small 的收益代替 70B 的完整速度对照。

## 完成检查与解释边界

- 四个点实际配置均匹配输入；每点完成 1/1 请求，无拒绝、未完成、审计失败或回滚，均有一个 prefill 和三个 decode cohort。
- 各 cohort 的命令和流量汇总与总账一致；HBM burst 数等于读写命令数之和，物理字节数等于 burst 数乘以 32。全部 HBM 访问均通过 JEDEC 控制器；其中约 95.76%–96.37% 使用编译核心，其他少量请求使用相同规则的参考执行路径。
- 最终源码的 595 项测试和 33 项子测试通过。四组 Small 完整结果与参考逐字段、浮点逐位一致；70B 四点各前 64 次请求（共 256 次）也精确一致。前缀检查不等于完整旧新版 70B 对照。
- 所有时序仍为有出处的工程参数，厂商标定未完成；这次不是实机测量。
- 本实验 HBF 配置为 `generic_nand / analytical_page_service`，不能写成完整 OCP 0.7.0 协议执行验证。此轮速度优化没有改变原实验的 HBF 建模方式。
- 每点只有一个请求、三个后续 token，不能据此推断尾延迟或长期稳定吞吐。四点 goodput 均为 0，原因是后续 token 超过设定的 100 ms TBT 门槛；输出已全部完成。
- 235B 按用户要求保持暂停，未补跑；本轮完成仅指这四个 70B 点。
